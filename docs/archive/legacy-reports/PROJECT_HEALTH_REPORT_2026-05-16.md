# MagicPodcast 项目体检报告

日期：2026-05-16

## 一句话判断

MagicPodcast 已经不是一个简单原型，而是一个有真实数据、真实工作流、真实使用习惯的个人生产系统。接下来最重要的不是继续堆功能，而是先把数据安全、开发验证、脚本入口、核心体验和工作流边界稳定下来。

## 当前优势

1. 产品方向清楚：播客管理、工作流、报告、搜索和标签已经形成了完整雏形。
2. 技术边界相对清晰：后端、前端、数据库、脚本、文档各有独立职责。
3. 本地自用场景已经跑起来：数据库中已有大量真实播客和单集数据，说明项目已经进入可持续使用阶段。
4. 后续扩展空间大：CLI、个人知识管理、OpenClaw/个人助理、长期服务化都可以从当前结构继续演进。

## 主要风险

### 1. 数据安全还不够像生产系统

数据库已经很珍贵，但原先缺少标准化备份、验证和恢复流程。一旦同步、迁移或脚本误操作造成损坏，恢复成本会很高。

本轮已补齐：

- 数据库验证脚本：`scripts/verify-db.sh`
- 数据库备份脚本：`scripts/backup-db.sh`
- 数据库恢复脚本：`scripts/restore-db.sh`
- 备份恢复说明：`docs/BACKUP_RECOVERY.md`

### 2. 运维脚本有漂移

原先 `start`、`stop`、`restart`、`health` 的判断逻辑不一致，有些脚本看的是旧 PID 文件，有些看的是进程名，有些看端口。这会造成服务实际在运行，但健康检查误报，或者重启没有真正重启到新版本。

本轮已统一：

- 服务路径自动推断，不再写死本机绝对路径。
- 停止逻辑统一使用 `/tmp/magicpodcast-*.pid` 和端口监听兜底。
- 重启统一调用停止和启动脚本。
- 健康检查改为真实检查端口、HTTP、数据库和备份状态。

### 3. 测试依赖外部网络，导致信号不可靠

同步模块原先测试依赖外部播客 Feed。网络波动会让测试失败，甚至造成 goroutine 泄漏类问题难以判断。

本轮已改为本地测试 Feed，测试可以稳定验证同步流程、超时、取消和并发连接。

### 4. 搜索分页存在用户可见问题

全局搜索接口中的单集分页参数没有真正生效，传 `episode_page=2` 时仍可能返回第一页结果。

本轮已修复：

- 播客分页继续使用 `podcast_page`。
- 单集分页改为使用 `episode_page`。
- 查询排序中的关键词处理改为参数化，降低特殊输入带来的风险。

### 5. 前端构建检查被关闭

前端配置里原先允许构建时忽略 TypeScript 和 ESLint 问题，这会让错误延后到运行时才暴露。

本轮已恢复：

- 构建时执行类型检查。
- 构建时执行 ESLint。
- 修复 Next.js viewport 配置警告。

### 6. 文档多，但缺少当前态地图

项目已有大量阶段性文档，但它们更像历史记录。后续需要保留历史，同时新增少量“当前真实状态”的文档，用来指导重构和需求迭代。

本轮已新增：

- 项目体检报告：本文件。
- 重构路线图：`docs/REFACTORING_ROADMAP.md`
- 备份恢复流程：`docs/BACKUP_RECOVERY.md`

## Gut Feeling

这个项目最值得押注的方向不是“做一个播客播放器”，而是“把播客变成个人知识流和自动化工作流的一等输入”。后续架构应该围绕三件事收敛：

1. 管理体验：让订阅、筛选、标注、清理、同步状态都足够顺手。
2. 工作流能力：让抓取、筛选、生成、汇总、导出、通知可以被稳定编排。
3. 个人系统融合：让 CLI、OpenClaw、知识库、自动化任务都能可靠调用 MagicPodcast。

短期最不该做的是重写一切。更好的策略是先把数据和验证地基打稳，再围绕真实使用路径一块一块替换。
