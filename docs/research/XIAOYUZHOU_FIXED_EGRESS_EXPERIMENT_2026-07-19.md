## 1. 决策范围

本报告对应 GitHub Issue #22。门槛是：在降频、去重和拒绝处理生效后，用同一批样本、同一请求参数和同一节奏，对比生产直连与一个可信且固定的备用出口，并在两个独立失败窗口中重复得到“直连失败、备用出口成功”。

本轮只判断是否已有足够证据进入固定出口评审，不为取得证据而换 IP、使用住宅代理、共享代理池、浏览器伪装、增加并发或无限重试。

## 3. 出口核对

2026-07-19 09:08（+08:00）分别在本机和生产机执行了不经过代理的公网出口核对，使用 `ifconfig.me/ip`、`api64.ipify.org` 和 `checkip.amazonaws.com` 三个服务。两台机器的三项结果一致；为避免把当前公网地址写入仓库，报告只保留脱敏标签和地址文本的 SHA-256 摘要：

- 本机：`direct-shared-nat`，摘要 `57d9f0db0ee949ec33af2586d38cab4cb4735d83b2f483c46ae5eb72179bac6e`。
- 生产机：同一 `direct-shared-nat`，同一摘要。
- 两台机器分别通过 `en0` 和 `en1` 连接到同一局域网出口；本次没有确认第二条独立公网路径。

本机还存在 `127.0.0.1:7892` 的 FlyingBird 进程。但仓库中的 PodcastIndex 升级运行手册明确限定它只用于 staging 数据集验证，不注入生产服务、不改变业务网络路径；它没有被当作 #22 的可信固定备用出口，也没有用于本实验。

因此，本轮没有可审计的备用出口组，不能把本机直连、生产直连或 FlyingBird 伪装成两个独立出口。

结论是固定出口策略 `NO-GO`，但不是“已证明 IP 无关”。未解决的候选因素仍包括请求节奏、时间窗口、CDN 边缘策略、统一上游规则和出口/ASN 相关性。

## 5. 操作与回滚边界

本轮没有：

- 部署中继、代理、NAT 或固定主备出口；
- 修改生产默认路由、DNS、Cloudflare Tunnel 或应用配置；
- 定期或逐请求换 IP；
- 对 Feed 做压测、批量探测或重复重试；
- 保存完整 Feed 正文、凭据、Cookie 或令牌。

因此没有新增生产变更需要回滚；现有代码提交仍可按票据独立回退，生产运行版本保持原样。#24 应按本报告进入 No-Go 收口，不应部署任何出口组件。

## 6. 后续重新打开 Go 实验的必要条件

只有同时具备以下条件，才重新打开固定出口对照：

1. 一个由所有者明确批准、单一负责人可追溯、长期地址稳定的备用出口；
2. 能记录该出口身份、DNS/CDN 结果、HTTP 状态、延迟、请求数和失败类别，且不记录敏感内容；
3. 降频、去重和拒绝处理已在要观测的运行路径中生效；
4. 使用本报告的同一 21 个样本、相同 User-Agent、超时、条件请求设置和请求间隔，交替测试且不并发压测；
5. 在两个新的独立失败窗口中重复记录两组数据。

在这些条件满足前，按 #35/#36 使用共享单队列、软限速、有界分类重试和已验证 PodcastIndex 替代源；last-good 只用于 304 恢复和诊断。不扩大出口池，也不把一次成功访问解释成 Go 证据。
