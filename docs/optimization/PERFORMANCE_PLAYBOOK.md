# MagicPodcast 性能专项工作手册

最后更新：2026-08-09

本文沉淀 MagicPodcast 在全站加载、工作流执行历史、播客分页、图片加载和首页发现台专项中的共同经验。它规定性能专项如何定义问题、选择方案、验证用户体验和完成生产收口。

性能数据会随代码、数据量和运行环境变化。本文记录的是长期方法；当前数值以 [性能基线](../performance/BASELINE_2026-05-31.md) 和重新执行的测试结果为准。

## 1. 核心定义

性能优化的成功标准不是“请求更早结束”，而是：

> 用户更早看到可用内容，已有内容不会因慢请求或失败而消失，并且结果能够被测量、监控和回退。

每个专项必须先写一条**用户体验不变量**，例如：

- 后端变慢时，首页仍有可用内容。
- 分页失败时，已经加载的节目仍然保留。
- 图片加载较慢时，页面布局和核心操作仍然稳定。
- 切换执行历史时，不因非关键图片或整页导航阻塞首批记录。

如果方案会改变加载态、空态、错误态、超时、缓存、陈旧数据或重试策略，属于用户可见行为变化，实施前必须单独人审。

## 2. 已验证案例与教训

| 专项 | 观察到的问题 | 真正根因或关键取舍 | 沉淀规则 |
| --- | --- | --- | --- |
| 全站、列表和工作流详情 | 页面和交互整体偏慢 | 查询、返回体积、请求数量、导航和渲染成本混在一起 | 将数据查询、网络、渲染和交互分别测量；不要用单一页面总耗时解释全部问题 |
| 工作流执行历史首屏 | 点击历史标签后首批记录出现较慢 | 整页路由切换、预取时机和非关键封面请求争抢关键路径 | 局部状态切换避免不必要的整页导航；只预取下一步最可能需要的摘要；非关键资源不得抢占首屏 |
| 播客分页与虚拟列表 | 分页挂起、快速触发重复请求、失败后内容消失 | 缺少有界超时、触发去重和已加载内容保留 | 分页必须有有限超时、单次触发去重、失败页单独重试，并保留之前成功的页 |
| 图片加载 | 列表和工作流封面逐张出现、流量大 | CDN 缓存实际命中；主要浪费来自过大原图、延迟挂载、错误观察容器和缓存键噪声 | 先证明缓存命中，再优化尺寸桶、格式、首屏挂载和稳定缓存键 |
| 首页发现台首次加载 | 后端慢时首页等待约 34 秒 | 首屏依赖客户端完整请求；仅增加超时会让请求更快结束，却可能暴露空错误态 | 首响应只取必要内容，完整列表后台刷新；优先保留历史内容，无历史内容才显示骨架，真正失败后再提示 |

图片专项中，桌面列表 15 张封面冷载曾从约 7.63 MB 降至约 83 KB，下降约 98.9%。这项收益来自减少无效字节，而不是简单增加缓存层。

首页专项中，服务端首响应只读取 5 条候选，完整 30 条在客户端后台刷新；2.5 秒超时保留，但慢请求时优先显示上次成功内容。受控慢后端测试中，有缓存场景的有效内容约在 2.61–2.68 秒出现，空内容暴露为 0/5。生产回环入口的三轮巡检首页 P95 为 455 ms；该数值只代表当次发布验收，不替代后续基线更新。

图片发布曾在本地和初始生产检查通过后，因为持续公网门禁出现超时而自动回退。这证明“代码有效”和“版本可稳定留在生产”是两项独立结论。

## 3. 根因分析顺序

性能专项默认只读诊断，先建立基线和证据链，再提出修改。

### 3.1 先确认真实运行对象

至少确认：

- 当前源码、分支和提交；
- 本地或生产实际运行的 release；
- 当前配置、缓存边界和数据规模；
- 测量使用的是冷态、热态、回访还是滚动返回场景；
- 入口是本地开发、生产回环还是认证公网。

不能用源码中的配置推断运行态已经加载，也不能用本地结果代替生产结论。

### 3.2 拆解完整链路

按实际问题选择链路，不要从症状直接跳到结论：

```text
用户动作
  → 页面导航或交互
  → React / Next 渲染与挂载
  → 浏览器请求与调度
  → API / 图片代理
  → 服务与数据库
  → 上游资源
  → CDN / Tunnel / 认证公网
```

图片慢时应分别检查真实显示尺寸、下载尺寸、请求开始时间、缓存响应头、边缘命中和热重载传输量。页面慢时应分别检查服务端响应、有效内容出现、客户端刷新、资源竞争和重复渲染。

### 3.3 先定位浪费，再讨论资源

方案优先级固定为：

1. 取消不必要的请求、查询和重渲染；
2. 缩小单次返回体、图片尺寸和资源体积；
3. 让关键内容先执行，非关键工作后台化；
4. 复用上次成功结果或当前已加载内容；
5. 增加有界缓存、单飞和失效策略；
6. 最后才调整并发、超时和重试。

并发只能缩短可并行的必要工作，不能修复重复请求、错误数据形态、过大资源或错误挂载时机。

## 4. 方案设计规则

### 4.1 关键路径

对每个用户动作明确：

- 第一批必须出现的内容；
- 可以后台完成的内容；
- 不应与关键内容竞争的资源；
- 允许显示旧内容的时间和提示；
- 真正失败的判定条件。

预取只服务于明确的下一步意图。批量预取全部数据或图片可能反而拖慢当前页面。

### 4.2 缓存

缓存设计必须同时说明：

- 缓存键是否稳定；
- 容量和单项大小上限；
- TTL 和陈旧数据窗口；
- 失效触发条件；
- 并发相同请求是否合并；
- 失败是否会污染缓存；
- 用户是否需要看到“正在刷新”或“当前为上次结果”。

重试不得通过追加随机参数或 `_retry` 等方式制造无意义的新缓存键。

### 4.3 超时和重试

超时是资源边界，不是完整用户体验。

- 超时后有历史内容：保留内容并后台刷新；
- 超时后无历史内容：保持结构化骨架；
- 多次确认失败：提供轻提示和明确重试入口；
- 分页失败：只标记失败页，保留已加载内容；
- 明确不可恢复的拒绝：停止相同条件下的重复请求；
- 所有重试必须有限、有退避、可观察。

### 4.4 虚拟列表和延迟加载

虚拟化和懒加载不能只验证向下滚动，还应覆盖：

- 首屏直接挂载；
- 快速滚动；
- 滚动返回；
- 容器尺寸变化；
- 移动端和桌面端真实滚动容器；
- 元素卸载后重新挂载是否重复下载；
- 占位内容是否造成布局跳动。

## 5. 指标体系

性能专项至少同时记录响应、内容、资源和稳定性四类指标。

| 类别 | 指标示例 | 回答的问题 |
| --- | --- | --- |
| 响应 | TTFB、API 平均/P95/P99、超时率 | 服务什么时候开始返回 |
| 内容 | 有效内容出现时间、首批记录时间、空态暴露率 | 用户什么时候看到可用结果 |
| 资源 | 请求数、下载字节、图片候选尺寸、缓存命中、重复请求数 | 为结果付出了多少网络和计算成本 |
| 稳定性 | 错误率、重试次数、分页保留率、持续门禁成功率、回退次数 | 优化在失败和时间窗口内是否可靠 |

不要只报告平均值。冷启动、热态和 P95 至少分开记录；对明显长尾再补 P99。

`scripts/performance-audit.mjs` 适合页面/API 轻量巡检，但它不能单独证明有效内容出现时间、空态暴露率、真实浏览器资源调度或认证公网稳定性。

## 6. 固定场景矩阵

每项用户可见性能改动必须覆盖：

| 场景 | 必须观察 |
| --- | --- |
| 正常请求 | 内容、排序、交互与当前契约一致 |
| 慢请求 | 已有内容是否保留；无历史内容时骨架是否稳定 |
| 请求失败 | 何时提示；是否保留已有内容；重试是否可用 |
| 首次访问 | 无缓存、无历史内容时是否出现空白或提前报错 |
| 缓存回访 | 是否先显示上次结果并后台刷新；陈旧状态是否诚实 |
| 分页/滚动返回 | 已加载内容是否保留；是否重复请求或重新下载大资源 |

使用 [性能专项验收模板](PERFORMANCE_ACCEPTANCE_TEMPLATE.md) 记录场景、指标和证据。

## 7. 验证和发布证据

性能结论按层级分别证明：

1. **源码与测试**：改动存在，正常、慢、失败、首次访问测试通过；
2. **本地生产模式**：生产构建、页面/API 巡检、必要的浏览器资源证据；
3. **运行版本**：健康检查和 release 元数据指向目标提交；
4. **生产回环**：服务、数据库、页面和关键业务入口正常；
5. **认证公网**：真实入口的内容、资源和网络行为符合预期；
6. **持续门禁**：需要观察长尾或 Tunnel/CDN 稳定性时，在约定时间窗内持续通过。

本地测试、生产回环和认证公网不能互相替代。阻塞门禁出现一次失败，就不能把专项写成已成功收口；应停止关闭 Issue，并按预设路径回退或继续诊断。

生产发布和回退遵循 [发布检查清单](../RELEASE_CHECKLIST.md)，普通代码与文档验证遵循 [Agent 验证指南](../AGENT_VERIFICATION.md)。

## 8. 汇报口径

优先报告用户可观察结果：

- “慢请求时仍显示上次成功的 30 条候选，后台继续刷新。”
- “首次访问没有历史内容时显示骨架，多次失败后才出现重试入口。”
- “分页失败后前 60 条内容仍然可用。”
- “15 张列表封面冷载约 83 KB，热回访传输为 0。”

避免只写：

- “进入降级态。”
- “增加了缓存。”
- “P95 下降。”
- “本地测试通过。”

最终结论至少回答：用户多久看到什么、失败时还剩什么、生产运行的是哪个版本、有哪些检查未完成。
