# MagicPodcast 重构路线图

最后更新：2026-05-17

## 当前判断

未来两个月仍以自用为主，但代码已经开始按“长期个人服务”整理。当前重构不再追求大而全，重点是把每天会用、容易出问题、数据风险高的老功能先稳定下来。

当前主线：

1. 播客管理体验优先，范围包括播客列表页、详情页和单集列表。
2. 同步、搜索、导入、备份恢复优先稳定。
3. 不急着加新业务能力，先降低老功能维护成本。
4. 任何会改写真实数据的动作，都必须先有备份、验证和回滚路径。

## 已完成

### 地基与数据安全

- 建立数据库验证、备份、恢复脚本。
- 建立每日自动备份，并自动清理 14 天前的备份。
- 健康检查覆盖服务、数据库、备份和脚本入口。
- 完成历史脏数据体检和修复方案。
- 修复健康检查误报。
- 统一启动、停止、重启入口。
- 恢复前端类型检查、测试和页面规范检查。

### 同步稳定性

- 同步失败不再被误报成完成。
- 导入和同步的实时日志连接有明确完成确认。
- 同一个播客同步时复用已抓取的 RSS，减少重复网络请求。
- 单集同步会预加载已有单集，减少逐条查询。
- 已存在且未变化的单集不再重复写库。
- 同 GUID 但属于不同播客的单集不会被错误覆盖。
- 重试后成功的播客只计为成功，不再同时计入失败。
- 同步统计区分成功、失败、跳过、无更新。
- 降低同步页日志噪音，不再刷大量“正在抓取”日志。
- 后端同步流程已拆分为重试、统计、更新判断、单集同步计划等小模块。

### 导入和同步页面

- 导入临时文件使用独立文件名，并在结束后清理。
- 导入文案改为真实的“本地匹配模式”。
- 同步日志支持“无更新”独立筛选。
- 日志滚动行为修正：用户手动停留后，焦点保持不动。
- 导入页、同步页、日志面板、统计卡片、筛选按钮已拆成更小组件。
- 实时日志连接的请求、读取、完成判断、断流处理已拆分。

### 搜索与单集列表

- 修复搜索单集分页问题。
- 搜索处理逻辑按查询、分页、文本处理拆分。
- 播客详情页的单集分页加载已整理。
- 单集追加加载会去重，避免分页重叠导致重复显示。
- 从搜索结果跳到指定单集时，会按需要继续加载并定位。
- 单集列表的首屏加载、首屏失败、空列表、继续加载、全部加载完成等状态已拆成可测试逻辑。
- 单集卡片的封面、加载指示器、占位图、标题链接、播放按钮、备注展示等判断已拆成可测试逻辑。
- 后端单集列表接口已拆分为计数、查询、响应转换。

### 播客列表页

- 播客列表页主体已拆薄。
- 标签筛选、排序入口、列表状态、列表结果区已独立。
- 列表页的标签和排序状态整理为可测试的判断逻辑。
- 修复从带标签筛选的列表进入详情页后，返回列表丢失筛选的问题。
- 从列表进入详情页再返回同一列表时，会恢复原滚动位置。
- 关闭状态的移动端排序抽屉不再留在页面结构里，减少误读和误聚焦。
- 播客卡片的封面、简介、更新时间、单集数等展示判断已拆成可测试逻辑；卡片视觉保持原有样式。
- 播客列表的虚拟滚动行高、接近底部判断、继续加载触发已拆成可测试逻辑，并改为按真实可见区域判断，避免预渲染行导致过早加载。

### 播客详情页

- 播客详情页主体已拆薄。
- 备注编辑区已独立。
- 标签展示和编辑区已独立。
- 移动端和桌面端详情展示仍保持原行为。

## 当前状态

项目已经从“能跑”进入“可继续重构”的状态。备份、健康检查、测试、核心页面验证都已经有基础保障。

主要风险还在这几块：

- 播客列表页已完成第一轮拆分、基础连续性修复和继续加载触发保护；卡片视觉保持原有样式，后续只在明确确认后再动界面表现。
- 播客详情页仍然偏展示型，还不是一个高效工作台。
- 单集列表还缺少真正面向处理流程的状态组织。
- 搜索和同步虽然稳定了很多，但错误原因、重试结果和用户可见状态还没有完全形成闭环。
- 工作流功能仍然比较像功能模块，还不是可追踪、可放心托管的自动化系统。
- 脚本、旧文档、历史维护工具还需要继续收口。

## 近期路线图

### 阶段 0：地基收尾

目标：确保继续迭代前，数据安全和验证流程足够可靠。

优先待办：

1. 做一次恢复演练：从最新备份恢复到临时数据库，并跑完整健康检查。
2. 梳理脚本入口：保留官方入口，归档旧脚本和一次性维护脚本。
3. 建立“发布前检查清单”：测试、健康检查、数据库验证、备份状态。
4. 整理历史文档：把过期报告归档，保留当前路线图和操作手册。

完成标准：

- 能证明备份可恢复。
- 新改动提交前有固定检查步骤。
- 后续维护者不会被旧脚本和旧文档误导。

### 阶段 1：播客列表、详情页与单集列表继续重构

目标：把播客列表页、详情页和单集列表连成稳定的日常处理路径。列表页负责快速定位和筛选，详情页负责理解单个节目，单集列表负责进入具体处理。

优先待办：

1. 继续审视播客列表页：封面加载、继续加载中和“已经到底”的反馈是否清楚。
2. 检查列表页到详情页再返回列表页的连续性：筛选、排序和滚动位置已完成第一轮修复，继续观察真实使用中的边界情况。
3. 检查播客卡片：展示判断逻辑已拆出，视觉样式保持原状；继续用真实数据观察极端长标题、无简介、无封面等边界。
4. 继续拆播客详情页：把基础信息、描述、播放入口、标签、备注拆成稳定模块。
5. 统一详情页加载、空状态、错误状态和重试体验。
6. 梳理单集列表：首屏加载、继续加载、加载失败、重试、全部加载完的展示判断已完成第一轮拆分，继续观察真实数据下的边界。
7. 检查单集卡片：封面、加载指示器、占位图、标题链接、播放按钮、备注展示、日期、时长、文件大小等纯展示判断已完成第一轮拆分。
8. 列表页和详情页的视觉表现默认保持不动；如需调整信息密度，先单独确认再做。

完成标准：

- 播客列表页不再是一个臃肿入口页，筛选、排序和加载状态都容易维护。
- 从列表进入详情再返回列表，用户不会丢失关键上下文。
- 播客详情页代码继续变薄。
- 单集加载状态可预测，不会误触发重复请求。
- 详情页可以作为后续“工作台化”的稳定底座。

### 阶段 2：搜索与同步闭环

目标：让“找内容”和“同步内容”更可信。

优先待办：

1. 搜索侧继续拆分：把搜索结果展示、筛选、跳转参数恢复分开。
2. 同步页继续做体验审视：重点看日志密度、结果摘要、失败可读性。
3. 梳理同步错误原因：前后端使用同一套可读分类。
4. 给关键接口补最小集成测试：搜索、同步、标签、单集分页。
5. 检查同步过程中的数据库写入边界，避免无意义更新。

完成标准：

- 搜索跳转到详情页的路径稳定。
- 同步失败时能快速看懂原因。
- 同步完成统计和实际结果一致。

### 阶段 3：工作流能力整理

目标：先让现有工作流更可靠，再考虑扩展能力。

优先待办：

1. 梳理工作流创建、编辑、执行、报告展示的主路径。
2. 拆分工作流表单，减少大组件。
3. 检查报告展示层，继续降低富文本风险。
4. 整理执行历史和错误展示，让失败原因更清楚。
5. 为批量处理单集预留稳定入口，但暂不急着做新功能。

完成标准：

- 工作流相关页面更容易维护。
- 执行失败后能知道发生了什么。
- 后续做队列、批量处理、知识库导出时不用推倒重来。

### 阶段 4：CLI 与个人知识系统融合

目标：让 MagicPodcast 后续能被终端和个人助理稳定调用。

暂缓，但需要提前约束：

1. API 返回要稳定，避免频繁改字段。
2. 搜索、同步、导出、工作流执行要有清晰输入输出。
3. 重要结果优先支持机器可读格式。
4. 后续再设计 Obsidian、Logseq、OpenClaw 等连接方式。

## 下一步建议

最建议的推进顺序：

1. 先做备份恢复演练，确认“真能恢复”。
2. 接着审视并重构播客列表页，因为它是进入详情页和单集处理的主入口。
3. 然后继续播客详情页和单集列表重构。
4. 再回到搜索和同步页，整理失败原因与用户可见状态。
5. 最后进入工作流页面和执行链路。

原因：

- 备份恢复是所有真实数据操作的底线。
- 播客列表页决定“找节目、筛节目、进入处理”的第一步体验。
- 播客详情页和单集列表决定后续处理效率。
- 搜索和同步是内容流入系统的入口，稳定性会影响信任感。
- 工作流能力很重要，但应该建立在前面这些老功能更稳之后。

## 暂不做

- 不做多用户权限模型。
- 不做社交化功能。
- 不做重型微服务拆分。
- 不做全量重写。
- 不急着引入复杂任务队列，除非现有同步和工作流已经明确需要。

## 决策原则

1. 真实数据优先：涉及大量数据写入，先备份，再验证，再执行。
2. 老功能优先：先把现有导入、同步、搜索、播客列表页、详情页、单集列表做稳。
3. 页面先拆薄：复杂页面先拆结构，再谈新体验。
4. 自动化要可追踪：任何自动化都要能看到输入、输出、耗时和失败原因。
5. CLI 先稳定协议：先稳定输入输出，再做集成和快捷入口。
